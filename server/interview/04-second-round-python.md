# 二面：Python 并发与生产实践

本组题参考 [AI Agent Interview Guide](https://github.com/bcefghj/ai-agent-interview-guide) 中关于异步处理、性能、故障、测试和部署的问答，改写为当前 Python 3.14、FastAPI 与 LangGraph 技术栈下的深挖题。

## P13. FastAPI `lifespan` 适合做什么？

**参考回答：**

- 它在应用开始接收请求前执行初始化，在停止时释放应用级资源。
- 适合启动配置校验、连接池创建和后台资源清理，不适合执行耗时且无边界的业务任务。
- 初始化失败应让进程启动失败，而不是等首个真实请求才发现密钥或配置错误。

**项目落点：** 当前 lifespan 调用 `load()`，在启动时验证模型、OSS、token 和并发配置。

## P14. 线程、进程和协程如何选择？

**参考回答：**

- 协程适合原生异步 I/O，切换成本低，但任何阻塞调用都会拖住事件循环。
- 线程适合包裹阻塞 I/O 或释放 GIL 的原生计算，改造同步 SDK 成本低。
- 进程适合持续 CPU 密集且能承担进程间序列化成本的任务，也提供故障和内存隔离。
- 选择前先测瓶颈；模型调用占主导时，增加 CPU 进程通常没有意义。

**项目落点：** 现阶段以协程处理远端 I/O，用线程桥接同步库，没有额外自建进程池。

## P15. 如何判断事件循环被阻塞？

**参考回答：**

- 现象包括同一 worker 上无关请求一起变慢、健康检查尾延迟上升、CPU 长时间占满但异步任务没有推进。
- 先按 run ID 定位慢节点，再检查节点中是否直接调用同步 SDK、解析大文件或执行 CPU 密集循环。
- 用事件循环延迟指标、采样分析器和慢请求 trace 验证，不凭函数是否写了 `async` 判断。

**项目落点：** 同步提取、OSS SDK 和图片裁剪已经通过 `to_thread` 隔离；仍需用代表性大文件压测确认线程与内存上限。

## P16. 并发任务中部分失败应怎么设计？

**参考回答：**

- 先区分“任何一个失败都必须整体失败”和“成功子集仍有业务价值”两种语义。
- 可降级任务在子任务内部把异常转换成结构化结果，聚合层统一判断 `PARTIAL` 或整体失败。
- 不要无条件使用 `gather(..., return_exceptions=True)` 后忽略异常，否则错误类型、索引和可重试性会丢失。

**项目落点：** 视觉和 chunk 失败都保留阶段、索引、错误码和重试属性；全部 chunk 失败才终止。

## P17. 超时与取消应如何传播？

**参考回答：**

- 超时是调用方对等待时间的约束，取消是协程收到的控制信号；底层操作是否真的停止取决于使用的库。
- 捕获异常时不能用宽泛逻辑吞掉取消，否则任务可能继续占用连接或产生副作用。
- 对线程中的同步调用，取消 awaitable 不一定能终止已经运行的线程函数，因此还要依赖超时和资源上限。

**追问：** `asyncio.wait_for` 超时后应返回稳定业务错误，并确认被包装资源能正确关闭。

## P18. 如何给异步系统做背压？

**参考回答：**

- Semaphore 只控制正在执行的数量；还需要限制入口队列、请求大小、任务总数和等待超时。
- 上游提交速度长期高于下游处理能力时，系统必须排队、拒绝或降级，不能靠无限创建 Task 吸收流量。
- 模型并发和 OSS 并发应分别设限，因为瓶颈和失败模式不同。

**项目落点：** Agent Server 管理 pending/running runs，Graph 与 OSS 使用独立并发配置，文档输入还有大小、页数和字符上限。

## P19. 有 GIL 是否还会发生竞态条件？

**参考回答：**

- 会。一次看似简单的业务操作可能跨多条字节码，也可能在 `await`、I/O 或原生扩展处切换执行。
- GIL 不提供业务事务性，更不能保护多进程或远端服务上的共享状态。
- 共享内存用锁或避免共享；跨进程状态交给外部持久化服务。

**项目落点：** Graph State 不依赖普通全局变量，运行状态由 Agent Server 管理。

## P20. 多 worker 部署会怎样影响进程内缓存和连接？

**参考回答：**

- 每个 worker 是独立进程，拥有自己的 `lru_cache`、模型客户端、OSS 客户端和内存，没有跨进程单例。
- worker 数翻倍时，内存和潜在模型并发也会一起增长，必须重新核算总预算。
- 需要跨进程一致性的状态应放在 PostgreSQL、Redis 或其他外部系统，不能放普通全局变量。

**项目落点：** 运行状态和 checkpoint 由 Agent Server 的 PostgreSQL 保存，Redis 用于流与队列协调。

## P21. 如何控制 Python 进程的内存峰值？

**参考回答：**

- 避免在 Graph State 中保留文件字节和 Base64；保存 OSS 引用并按需读取。
- 限制单文档页数、像素、解压后大小、文本字符、题目数和并发任务数。
- 大对象的瞬时副本也要关注，例如读取、哈希、解码、渲染和序列化可能同时保留多份数据。

**项目落点：** 容量脚本可采样进程 RSS，但阈值通过不代表没有短时峰值，仍需结合更高频采样和代表性输入。

## P22. 如何定位 Python 服务的性能瓶颈？

**参考回答：**

1. 先用指标判断是排队、CPU、内存、网络、OSS 还是模型供应商。
2. 用 trace 找到慢节点，并区分等待时间与本地执行时间。
3. CPU 问题使用采样分析器，内存问题比较 RSS、对象分配和代表性输入规模。
4. 一次只改一个参数，用同一负载复测 P50/P95/P99、错误率和资源峰值。

**追问：** 不应把“改成 async”当作通用优化；如果瓶颈是模型限流或 CPU 解析，它可能毫无帮助。
