# 二面：生产工程与系统设计

这一组用于压力面和扩展追问。回答要区分“代码已有约束”“部署文档中的基线”和“真实环境实测结果”。

## 31. 没有配置视觉模型时会发生什么？

**参考回答：**

- 含文本的混合文档仍可解析，但视觉单元会被跳过，结果标为 `PARTIAL` 并给出 warning。
- 纯图片文档没有可提取文本时返回 `VISION_MODEL_REQUIRED`，不会伪造空结果。
- 这是能力降级而不是静默成功，调用方可以决定是否接受。

**深入追问：** 为什么不自动用文本模型处理图片？模型能力和输入协议不同，错误兜底可能制造不可观测的质量下降。

## 32. 系统有哪些输入和资源上限？

**参考回答：**

- 默认源文件 25 MiB、PDF 100 页、派生视觉内容 50 MiB、单页 2500 万像素。
- 模型总输入默认 200 万字符，单次输出默认 16,384 token，模型调用超时默认 180 秒。
- 题目、题组、视觉元素、裁图和压缩包条目也有数量或解压大小限制。

这些限制应在部署前结合真实文档分布校准，不能只照搬默认值。

**深入追问：** 为什么限制解压后大小而不只限制上传大小？小型压缩包可能解压成超大内容，造成 zip bomb 风险。

## 33. 系统如何限制并发，为什么不能只调大 worker 数？

**参考回答：**

- `N_JOBS_PER_WORKER` 控制活跃 run，`AI_GRAPH_MAX_CONCURRENCY` 控制单 run Graph 并行度。
- 启动时要求两者乘积不超过 16，避免理论模型并发超过基线。
- OSS I/O 另由 `AI_OSS_CONCURRENCY` 限制，防止把模型并发与存储并发混为一个旋钮。

**深入追问：** 应该先调哪个参数？先看 pending、运行数、模型 429、CPU、内存和 OSS 延迟，一次只改一个参数后重测。

## 34. 上线后至少监控什么？

**参考回答：**

- Agent Server：pending runs、running runs、available workers、HTTP 延迟。
- 应用结果：`PARTIAL` 比例、重试耗尽、checksum mismatch 和各阶段失败码。
- 资源：容器内存、主机磁盘、PostgreSQL 磁盘和外部模型限流。
- 日志按 run ID 串联，模型调用还记录 model ID、token 和 `callKey`。

**深入追问：** `/ok` 正常是否代表业务健康？不代表，它只能说明服务存活，不能证明模型或 OSS 可用。

## 35. 线上反馈“有时很好，有时很差”，如何排查？

**参考回答：**

1. 固定具体 run ID，不先凭感觉改 Prompt。
2. 查看输入格式、文件截断、视觉跳过、失败单元、重试次数和模型版本。
3. 区分提取错误、OCR 错误、chunk 边界、模型结构错误或语义错误。
4. 用同一输入稳定复现，再决定改提取器、Prompt、输出 Schema 还是模型。

**深入追问：** 为什么平均成功率不足以定位问题？不同格式、页数和题型的失败分布可能完全不同。

## 36. 如何设计 Benchmark？

**参考回答：**

- 固定模型版本、参数、代码版本和代表性文档集。
- 质量指标：题目级准确率/召回率、题型与选项准确率、原文答案提取准确率和结构合法率。
- 稳定性指标：部分失败率、重试次数和恢复成功率。
- 成本与性能：模型调用数、输入/输出 token、端到端延迟和资源峰值。

当前仓库提供测试与压测工具，但没有可据此声称领先的完整业务评测结果。

**深入追问：** 为什么结构合法率不能代替语义正确率？格式正确的题目仍可能被错误切分或理解。

## 37. 容量测试验证什么？

**参考回答：**

运维基线使用独立 thread 批量提交文档任务，检查 run ID 唯一、全部进入成功终态、run 创建和健康检查 P95、活跃 run 上限、配置并发上限及进程 RSS。压测还必须保留 provider 侧并发图，确认真实模型峰值没有超过预算。

脚本中的阈值是验收规则，不代表当前环境已经完成同规模实测。

**深入追问：** 为什么每个任务用独立 thread？避免同一 thread 的排队和状态语义污染并发结果。

## 38. 生产安全边界有哪些？

**参考回答：**

- Agent Server 和自定义上传路由使用 Bearer service token，并用常量时间比较。
- 密钥通过部署平台 secret 注入，不写入镜像或仓库。
- OSS 下载校验大小与哈希，文档解析器限制页数、像素、解压规模和输入长度。

**深入追问：** 一个固定 service token 的局限是什么？它只能标识服务身份，无法提供细粒度租户授权和轮换审计；有多调用方需求时再升级身份模型。

## 39. 发布前应做哪些故障演练？

**参考回答：**

- 处理中重启应用，验证同一 run 恢复且没有重复终态。
- 注入 LLM 429、连接超时和 OCR 非法输出，验证四次总预算与错误分类。
- 让单个和全部 chunk 分别失败，验证 `PARTIAL` 与整体失败边界。
- 注入错误大小或 SHA-256，确认在模型调用前失败。
- 暂停并恢复 Redis，确认流受影响但 PostgreSQL 中的权威 run 不丢失。

**深入追问：** 故障演练为什么要对发布候选镜像执行？本地源码通过不等于镜像配置、依赖和基础设施组合正确。

## 40. 什么时候需要从单机扩展到分布式？

**参考回答：**

- 当前单机基线只承诺应用进程重启恢复，不承诺主机级高可用。
- 先通过容量测试证明单机在 CPU、内存、队列或可用性目标上不足。
- 再采用 Agent Server 官方的 split API/queue 或分布式形态，而不是先引入 Celery、Kafka 或自建队列。
- 扩展后仍需重新验证 checkpoint、队列积压、限流和故障恢复。

**深入追问：** 为什么 PostgreSQL 和 Redis 已经外置仍不等于高可用？应用仍有单主机故障点，外部服务本身也需要各自的高可用配置。
