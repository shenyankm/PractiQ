# 一面：项目基础与工作流

回答必须以当前仓库实现为准：项目只有文档理解能力。

## 1. 请用两分钟介绍 PractiQ AI Server

**参考回答：**

- 它把 PDF、图片、Word、Excel、CSV 或文本转换为结构化题目与视觉素材。
- 仓库只注册 `document_parser` 一个 LangGraph 工作流。
- 核心难点是多格式提取、视觉与文本分片并行、结构化校验、稳定合并和部分失败处理。

**常见追问：** 你本人负责了哪一段？最难的问题是什么？

## 2. 为什么使用 Workflow，而不是开放式 ReAct Agent？

**参考回答：**

- 文档处理阶段、合法分支和结束条件都已知，属于高约束任务。
- Graph 显式表达节点、条件边和并行任务，比让模型自由选择工具更可控。
- 模型只负责语义理解；鉴权、对象校验、路由、合并和错误分类由确定性代码负责。

**常见追问：** 什么业务场景才更适合 ReAct？

## 3. 六种输入格式如何收敛到统一流程？

**参考回答：**

- `extractors/` 隔离 PDF、图片、DOCX、XLSX、CSV 和文本的格式差异。
- 提取器统一产出正文、页图、内嵌图片、告警和截断标记。
- 后续节点只处理统一结构，不再分支判断文件格式。

**常见追问：** DOCX/XLSX 为什么要限制压缩包条目数和解压后大小？

## 4. 文档解析的完整执行链路是什么？

**参考回答：**

1. 客户端调用 `POST /api/uploads` 获取预签名信息，再把二进制直传 OSS。
2. `prepare` 校验对象大小和 SHA-256，并提取文本、页图和内嵌图片。
3. `vision` 通过 `Send` 并行处理视觉单元，`assemble` 汇总文本并生成分片。
4. `chunk` 并行解析各分片，`merge` 按索引稳定合并、去重和裁图。
5. 最终返回 `SUCCEEDED` 或带失败明细的 `PARTIAL`。

**常见追问：** 为什么文件不直接作为 Graph State 的 Base64 输入？

## 5. 项目算 Agent 或 Multi-Agent 吗？

**参考回答：**

它更准确的表述是“由 LangGraph 编排的文档理解工作流”。多个并行 LLM task 不等于多个自治 Agent 协作，当前也没有工具自主选择、角色交接或独立 Agent。

**常见追问：** 为什么还使用 LangGraph？因为并行任务、状态归集、失败降级和 checkpoint 都是工作流需求。

## 6. 结构化输出如何保证？

**参考回答：**

- 模型使用 Pydantic Schema 输出题干、题型、选项、原文答案和素材块。
- 跨字段校验确保选择题有选项、答案类型与题型一致、选项标签唯一。
- 合并阶段继续检查索引、上限和重复题干；结构合法不等于语义一定正确，因此还需要评测集。

## 7. 当前能力边界是什么？

**参考回答：**

项目不提供独立答案生成、题库写入、RAG、向量数据库、长期记忆或多智能体协作。当前评测是公开合成小样本和本地真实服务基线，不能表述为生产验证。
