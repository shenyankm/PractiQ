# 多文档吞吐优化与验证（2026-09-19）

已修复本地启动命令没有落实任务并发配置的问题，补充分段耗时观测，并完成真实模型配置对比。保留 `8×2` 默认值；`16×1` 仅作为短文档批处理的可选配置。

## 已落实的改动

- `make server-dev` 显式设置 CLI 的 `--n-jobs-per-worker`，优先读取进程环境，其次 `server/.env`，缺省 8。当前安装的 dev runtime 原先覆盖 `.env` 的同名配置，未传参数时实际使用 1。
- 增加并发槽等待、RPM 等待和 SDK 请求耗时；保留原有总调用耗时、调用预算、限流顺序、失败用量和 checkpoint 行为。
- 压测在每个任务提交后立即轮询，新增批次耗时、成功吞吐和用于复核的 thread/run ID；评测记录新增三段模型耗时。

启动复现实验：同样设置 `N_JOBS_PER_WORKER=8`，原命令的 `/metrics` 显示 worker 上限 **1**，修复后的真实 Makefile 启动显示 **8**。这是并发配置生效的验证，不是宣称整体速度提高八倍。

证据：[启动验证](evaluations/throughput-20260919/launcher-check/result.json)。

## 真实模型对比

- 本地、loopback Agent Server，真实 DashScope `qwen3.7-flash`；非 mock、非生产环境。
- 两种配置按 `8×2 → 16×1 → 16×1 → 8×2 → 8×2 → 16×1` 交替，每种三轮。
- 每轮先独立预热，再突发提交 24 份相同短文本、8 份相同四页 PDF。共 **192 份文档、336 次计入测量的模型调用**，另有 6 次预热调用。
- 同一代码、同一 gold 数据和同一模型；供应商本地限制均为 16 并发、120 RPM，采用原有 function calling。每次使用独立服务状态和文件目录。
- 复用现有 gold scorer 检查题目、选项、答案、分组及图形类别；服务成功与内容评分分开统计。

下表耗时和吞吐均为三轮统计值的中位数，P95 为各轮 P95 的中位数。

| 场景 | 配置 | 批次耗时 | 完成 P95 | 观测排队 P95 | 内容评分通过 | 合格文档/分钟 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 24 份短文本 | 8×2 | 13.154 秒 | 12.942 秒 | 8.935 秒 | 72/72 | 109.47 |
| 24 份短文本 | 16×1 | 9.605 秒 | 9.553 秒 | 5.889 秒 | 72/72 | 149.92 |
| 8 份四页 PDF | 8×2 | 132.024 秒 | 129.665 秒 | 1.201 秒 | 22/24 | 3.18 |
| 8 份四页 PDF | 16×1 | 142.024 秒 | 141.295 秒 | 1.186 秒 | 23/24 | 3.38 |

短文本批次耗时下降 **27.0%**，合格吞吐提高 **37.0%**。四页 PDF 三轮耗时分别为 `141.429 / 132.024 / 75.107` 秒与 `163.167 / 142.024 / 77.761` 秒；供应商耗时变化明显，不能把小样本质量或吞吐差异解释为稳定的模型质量提升。

全部 192 份均返回 `SUCCEEDED`，但有 **3 份 PDF 内容评分未通过**。这说明服务成功不能替代质量验收，PDF 性能对比是诊断数据，不能作为通过质量门禁的发布基线。未改 gold、提示词、模型或质量规则。

336 次测量调用没有本地记录的供应商错误或纠错/重试。客户端并发槽等待最大 **0.015 ms**，RPM 等待最大 **0.024 ms**，主要耗时在实际 SDK 请求中；该时间包含网络、供应商排队和生成，不能进一步归因到纯推理。最大采样服务进程 RSS 约 **0.884 GiB**，不包含整个机器或所有子进程的总内存。

## 采用与边界

- 默认保留 `N_JOBS_PER_WORKER=8`、`AI_GRAPH_MAX_CONCURRENCY=2`；启动修复使配置实际生效。
- 明确以短文档突发处理为主时，可将 `server/.env` 中的 `N_JOBS_PER_WORKER`、`AI_GRAPH_MAX_CONCURRENCY` 分别改为 `16`、`1` 后重启。不要只设置临时 shell 变量：当前 dev runtime 会载入 `.env` 中的 graph 并发值。修改部署并发前仍需核实实际供应商额度，不能只增加任务数。
- 不移除相邻页上下文、PDFium 安全锁、严格输入校验或失败记录；本轮数据不支持优先加进程池、改限流顺序或引入缓存服务。
- 只有两个重复的公开合成样本，未覆盖混合格式、长时间饱和流量、TPM 上限、真实业务文档、生产数据库或多 worker。8 份 PDF 的突发量也低于 16 个任务槽，不能推断更大批次长文档的表现。
- 重复源文件可能受到供应商隐式缓存及服务波动影响；未控制供应商缓存。轮询时间含观测误差；本地 dev 的 worker/queue 指标可能更新滞后，未以短任务期间的零值宣称无排队。视觉语义及图形 artifact 完整性未在本压测中重新验收。
