# PractiQ AI import Web

This React/Vite frontend uses the personal service Bearer token to upload source documents, inspect tasks and download question-bank ZIPs. Practice remains in the offline app. No account, phone, products, point balance or checkout is required. See [personal use](../server/docs/personal-use.md).

```sh
npm ci --prefix web
npm --prefix web run dev
npm --prefix web run check
npm --prefix web run test:browser
npm --prefix web run build
```

Development binds to `127.0.0.1:5173` and proxies `/api` to the loopback service on port `8090`. Production builds into `web/dist`; the independent service serves those assets from `/` when available and can also run without Web assets. API requests use the same origin as the page. The service access token is entered into a password field, kept only in page memory and cleared on reload. Provider credentials and model configuration stay on the server. No credentials are saved in browser storage or included in URLs.

The sidebar separates **Start import**, **Import history** and **Settings**. Start import accepts at most ten files and uses the service's supported formats and source-specific limits. Selection is passive; explicit Start computes SHA-256, uploads exact bytes and creates tasks with stable request IDs. Leading and trailing filename whitespace is trimmed for format checks and upload metadata, matching the service; file contents are unchanged. Every supported source uses Tencent recognition before question structuring; oversized inputs are prepared/split by the service. Failed files and frozen deduplication options survive navigation and reselection within this page. Unresolved creation requests also retain their original IDs, verified references and options across reloads in browser storage; explicit retries reuse them. Files not yet uploaded must be selected again. When the selected batch completes submission and no pending files remain, the page opens its import history automatically.

Task-creation errors `OFFICE_NOT_CONFIGURED` and `TENCENT_NOT_CONFIGURED` are definite admission rejections: no task was created, so correct the service configuration and retry explicitly. The Web frontend preserves the request ID but never retries automatically. Network failures, timeouts and other server failures still retain the unknown-outcome warning; inspect saved tasks before resubmitting those requests.

Import history shows filenames, state, separate question and review-count columns, and creation times. Background read failures retain the last list with a stale-data notice and disable paging until a successful read; switching filters or pages still clears the old list. Selecting a record opens progress, source/result review, model usage and the server-authorized pause, resume, retry and cancel actions. Cancellation retains the task and its partial results; deletion remains a separate confirmed action. Navigation and settings changes never start model work.

Settings are shared by the entire service and stored in PostgreSQL, across browsers and service restarts. The authenticated `GET /api/import-settings` returns a revision and current settings; `PUT` requires that revision, rejecting stale writes with `IMPORT_SETTINGS_CONFLICT`. The defaults are five Tencent workflows, two retries after a failed known-job read, and a one-second base backoff. Concurrency is restricted to 1–5, retries to 0–5, and base delay to 0.5–10 seconds. Lowering concurrency drains existing workflows before admitting more; in-flight requests are not interrupted. Each read captures its retry policy when it begins, doubles the delay with jitter and obeys the saved run deadline. Paid submission, authentication/permanent errors and unknown outcomes never gain automatic retries. Saving settings does not change model/provider credentials, document-worker/LLM allocation or existing conservative call reservations. Failed or uncertain saves retain the draft; explicitly reload to reconcile. Read-only service mode permits reading settings and rejects writes.

Polling only reads task lists, heads, details and previews. Processing tasks refresh every 3 seconds; quiescent tasks refresh every 30 seconds. Hidden pages pause polling and focus/visibility restores a fresh read. After the initial detail and preview, unchanged completed tasks use the authenticated `/api/document-tasks/{threadId}/head` response. Lists use `nextCursor` for subsequent pages, bound to the same filter; the service retains offset compatibility. Resume, retry failed units, accept partial results, pause, interrupt, reparse and delete require their corresponding actions. Checkpoint actions and export stay disabled when the latest detail and preview disagree or cannot be read. Task deletion requires confirmation, including expired tasks whose detail and preview are unavailable. An expired row can be deleted directly from the list; a pending or failed deletion retains its confirmation, and failures require an explicit retry. Completed partial results can be exported without changing their status, warnings, review flags, missing values or source associations. ZIP downloads use authenticated requests for the current checkpoint and the same 300 MiB archive ceiling as the service and native importer. In the desktop app, **Settings → Import and restore → Import bank ZIP** appends the downloaded bank.

The import workspace uses the existing octopus brand and blue action tokens. Wide windows use a persistent sidebar and dedicated import, history and settings content. The import form keeps supported formats, file limits and the paid-work warning next to the controls; format rules and call budgets are collapsed below it. Repeated page descriptions and workflow/footer copy are omitted. Settings retain only input bounds, retry semantics and the connection lifecycle. Narrow windows use the same three navigation destinations above stacked record details without page-wide horizontal scrolling. Keyboard users can skip the header, jump from the selected task to its details, and return to the task list. Browser Back/Forward and direct `#task-detail` / `#task-list-heading` links open the Import history page; shared anchors keep the current page. Narrow/touch layouts provide 48 px action targets. Failed capability verification is shown as a failure, not an indefinite connecting state; retry remains explicit. Result-view buttons expose their selected state to assistive technology.

Result review displays questions, parent material, shared options, source units, quality records and immutable image references without adding answers. Partial results, original warnings, missing fields and review requirements share one visible notice region. Same-task checkpoint updates preserve search, review filtering, the selected tab, pagination and expanded questions with stable identities while refreshing their content. Selecting another task or explicitly refreshing task details resets the review; either action also recovers a caught result-rendering failure without replaying task operations. Document/model HTML is inert; external Markdown images and links never make requests. Math renderers use the pinned top-level KaTeX version through npm overrides so their generated classes match the imported stylesheet. Source associations, quality JSON and OCR checksums are available in collapsed technical disclosures after readable resources. Quality JSON is formatted only while its disclosure is open on the Sources tab and reused during pagination. Images are fetched only on an explicit click through the authenticated artifact endpoint, checked against MIME, byte size and SHA-256, then displayed through a temporary blob URL. Unread response bodies are cancelled when a size, format or HTTP error rejects the response. Image and download URLs are released after use. Known model usage and calls with unknown usage remain distinct.

KaTeX keeps all 20 font faces in WOFF2, supported by Vite's modern browser targets; redundant WOFF/TTF fallbacks are excluded. The result review remains lazy, so this reduces complete static assets rather than initial JavaScript/CSS. The [October 9 measurement](../docs/history/performance/performance-web-fonts-20261009.md) preserves before/after samples and limits. Run `PRACTIQ_WEB_BUILT=1 npm --prefix web run test:browser -- --grep 'all KaTeX font faces'` from the repository root after building to verify every font face against production assets with synthetic HTTP responses.

Vitest uses at most two workers and enforces the existing desktop coverage thresholds (80% statements, 73% branches/functions, 85% lines). Playwright uses one Chromium worker on loopback port `1671` and intercepts every API request with synthetic HTTP responses. Its ZIP fixture checks download transport and bytes; native ZIP compatibility is covered by the shared service/desktop contract and native tests. These browser tests do not run a model, Office conversion, or a real service. A separate bounded hosting smoke may load built assets from a disposable read-only local service with model configuration absent; that checks static hosting, authentication and passive file selection, not live AI parsing or production deployment.

The service token stays only in page memory and clears on reload. Only explicit import/control actions start model work; task reads and ZIP exports remain passive.

## Interrupted imports and page reloads

Task state, checkpoints, call receipts and results belong to the service. Closing the page does not cancel an accepted task. Reconnect with the service token and open Import history to read its current progress. File selection and reconnection never start parsing.

Before task creation, the Web client saves the original request ID, verified document reference and import options in origin-scoped `practiq-import-intents-v1` browser storage. It saves no token or file contents. After reload, the recovery panel offers an explicit retry with the exact original payload: an accepted request returns its original receipt; an unaccepted request may start parsing and incur charges. Reselecting that source reuses the pending request and its original options. Storage errors prevent a new task submission; malformed records are retained for investigation. At most 50 unresolved submissions are retained. Clear a recovery entry only after checking service history; clearing it does not cancel the service task and a later new submission may incur another charge. Browser storage deletion or a different origin loses these local recovery hints; service history remains authoritative.

Reparse actions use the same explicit recovery rule. Before sending, the client saves only the original task ID and request ID in `practiq-reparse-intents-v1`, with at most 50 unresolved reparses and one per original task. Reloading or reconnecting never resends them. The recovery panel lets you inspect the original task, retry its exact request, or clear the hint after checking service history. A confirmed receipt removes only that request; a later new reparse receives a new ID. Invalid, ambiguous or unavailable browser storage blocks a new reparse and retains existing records. No token or source content is stored. Clearing a hint does not cancel an accepted task, and another reparse may incur another charge.

Model transport failures, HTTP 408 and provider 5xx responses stop with `MODEL_RESULT_UNKNOWN` rather than automatically repeating a potentially paid call. Known usage, unknown-call receipts and completed checkpoints remain saved. The task detail shows the uncertainty and potential charge beside explicit resume/retry controls. Explicit recovery may make another call; quota/conflict rejections retain bounded backoff and known invalid outputs retain bounded correction.
