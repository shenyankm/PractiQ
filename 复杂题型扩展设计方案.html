1. 现状与差距盘点

以下为逐题型核对后的现状（依据 db/00_schema.sql、backend/src/practiq_backend/content.py 的 normalize_key/validate_key、practice.py 的 grade()、web/src/pages-practice.tsx 的渲染分支）：

题型现状说明与缺口
单选题已支持choice + choice_variant='single'，选项表、答案键、自动判分、练习渲染（RadioGroup）全链路可用。无需改动。
多选题已支持choice_variant='multiple' 集合判分（全对才得分）、前端 Checkbox 渲染均已在位。无需改动（仅结果页渲染可优化，见 §4）。
判断题已支持true_false，键 {"answer":bool}，作答 {"value":bool}。无需改动。
填空题部分支持多空（键/作答均为有序列表，按行一一对应）。缺口：每空仅一个可接受答案（无同义/别写）、只有全对/全错（无按空部分得分）。
简答题部分仅存参考答案，grade() 对其恒返回 NULL（未判分）。缺口：无关键词自动判分、练习页无自评回写入口（只提示"请对照参考答案自查"）。
排序题缺失无 answer_mode、无条目存储、无判分。
连线题缺失同上。
组合题 / 材料题部分question_groups（材料、说明、状态、目录、排序）+ question_content_blocks/media 组级富内容 + questions.group_id 已在位，管理端可建组、挂题。缺口：练习页不呈现组材料；开启练习时子题不保证连续出现；无组维度详情/列表筛选；无组维度成绩聚合视图。
扩展机制的本体在哪里？题型的唯一硬门闩是 question_types.answer_mode 上的 CHECK 枚举；questions.answer_mode 通过复合外键 (subject_id, question_type_id, answer_mode) 被注册表间接约束。答案结构不走列，而走 question_answer_keys.answer_payload / practice_answers.answer_payload 两个 jsonb 字段，且答案键按版本不可变（immutable_answer 触发器）。因此扩展题型 = 扩 CHECK + 注册新题型行 + （可选）建结构子表 + 判分函数加分支，天然具备"新增题型不动存量"的特性。

2. 数据库表结构设计

2.1 设计原则

  1. 1加法式迁移：只新增表、新增可空列、扩 CHECK 枚举，不改不删既有列；现有库走增量迁移 db/migrations/002_complex_question_types.sql，全新库直接更新 db/00_schema.sql（两份内容等价，00_schema.sql 仍是新库唯一权威）。
  2. 2结构进表、配置进 jsonb：排序/连线的条目（有唯一性、排序、外键诉求）落独立子表；判分策略、部分得分开关等低频配置放答案键 payload 内的 grading 块，避免为每个策略加列。
  3. 3镜像既有模式：连线题变体 matching_variant 完全镜像 choice_variant 的列 + 形状 CHECK 模式，保持"题表一行 = 一种题型形态"的既有直觉。
  4. 4判分口径向后兼容：grade() 对旧形状 payload（扁平填空串、无 grading 块的简答键）行为与现在完全一致。

2.2 迁移 DDL（可直接执行）

-- db/migrations/002_complex_question_types.sql   （作用于现有个人库；00_schema.sql 同步等价内容用于新库）
BEGIN;

-- 1) 放宽题型注册表门闩，注册新题型 ------------------------------------------
ALTER TABLE question_types DROP CONSTRAINT question_types_answer_mode_check;
ALTER TABLE question_types ADD CONSTRAINT question_types_answer_mode_check
  CHECK (answer_mode IN ('choice','true_false','fill_blank','short_answer','ordering','matching'));

INSERT INTO question_types (id, subject_id, display_name, answer_mode) VALUES
  ('ordering', 'general', '排序题', 'ordering'),
  ('matching', 'general', '连线题', 'matching');
-- questions.answer_mode 无自身 CHECK，经复合外键 (subject_id,question_type_id,answer_mode)
-- 引用注册表，注册行落地后题目即可引用；既有 4 行与既有题目外键不受影响。

-- 2) 排序题条目表 -------------------------------------------------------------
CREATE TABLE question_ordering_items (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  question_id bigint  NOT NULL REFERENCES questions,          -- 所属题目（级联删随 questions 无需声明，个人库按现有惯例不加 ON DELETE）
  content     text    NOT NULL CHECK (btrim(content) <> ''),  -- 条目文本（纯文本；图片走附录A扩展）
  sort_order  integer NOT NULL CHECK (sort_order > 0),        -- 展示次序
  UNIQUE (question_id, sort_order)                            -- 同题内次序唯一；判分引用 id，与内容解耦
);
-- 说明：不约束 (question_id, content) 唯一——重复文本条目在排序题中合法但易混淆，
-- 由录入端 UI 提示，不在库层禁止。

-- 3) 连线题条目表（左右统一存一张表，side 区分）--------------------------------
CREATE TABLE question_matching_items (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  question_id bigint  NOT NULL REFERENCES questions,
  side        text    NOT NULL CHECK (side IN ('left','right')),
  content     text    NOT NULL CHECK (btrim(content) <> ''),
  sort_order  integer NOT NULL CHECK (sort_order > 0),
  UNIQUE (question_id, side, sort_order)
);

-- 4) 连线题变体列（镜像 choice_variant 模式）-----------------------------------
ALTER TABLE questions ADD COLUMN matching_variant text
  CHECK (matching_variant IN ('one_to_one','many_to_one'));
ALTER TABLE questions ADD CONSTRAINT questions_matching_variant_shape
  CHECK ((answer_mode = 'matching') = (matching_variant IS NOT NULL));
-- one_to_one：每个右项恰被一题左项选中（经典一一连线，要求左右数量相等，应用层校验）
-- many_to_one：右项可被多个左项复用（分类/归组式连线）
-- 既有 CHECK (answer_mode='choice')=(choice_variant IS NOT NULL) 不受影响（ordering/matching 两态与其互斥成立）

-- 5) 自评回写时间戳 ------------------------------------------------------------
ALTER TABLE practice_answers ADD COLUMN reviewed_at timestamptz;  -- NULL=未自评；简答自评后回填

-- 6) 组合题支撑索引 --------------------------------------------------------------
CREATE INDEX questions_group ON questions (group_id)
  WHERE deleted_at IS NULL AND group_id IS NOT NULL;   -- 组详情列子题、?groupId= 筛选

COMMIT;
执行约束：PG 不能原地修改 CHECK，须 DROP 再 ADD（瞬时 ACCESS EXCLUSIVE 锁；个人库数据量下可忽略）。该迁移一次性执行、禁止重放（重放会在 ALTER 处报错，属预期保护，与"never reset an existing database"的项目红线一致）。

2.4 各题型 answer_payload / 作答形态与判分规则（核心契约）

本表是前后端共同的"题型协议"，键 = question_answer_keys.answer_payload（版本化、不可变），答 = 作答请求体中的 answerPayload 与落库的 practice_answers.answer_payload：

answer_mode答案键形态（v1 现状 → v2 扩展）作答形态判分规则（grade() 分支）
choice
单选/多选		 {"correct":["A","B"]}（现状） {"selected":["A","B"]} 集合相等 → 1 分，否则 0。不变。校验：labels 合法、无重复、single 恰 1 个。
true_false {"answer":true}（现状） {"value":true} 布尔相等 → 1/0。不变。
fill_blank v1：{"answers":["2"]}
v2：允许每空多可接受答案 {"answers":[["2","two","二"]]}（字符串元素=单答案，数组元素=可接受集合，二者混用合法）；可选 {"grading":{"mode":"blank_ratio"}}		 {"value":["2"]}（按空有序） 逐空归一化（casefold + 空白折叠）比对，实际值 ∈ 该空可接受集合即该空正确。默认全对得 1、否则 0（与现状一致）；blank_ratio 时 score = 正确空数/总空数，is_correct = 全对。
short_answer v1：{"answer":"参考"}
v2：可选 {"answer":"参考","grading":{"type":"keyword","keywords":[{"text":"导数","weight":2}],"threshold":0.6}}		 {"value":"文本"} 无 grading 块 → is_correct=NULL（现行行为不变）；keyword → score = 命中关键词权重和/总权重，is_correct = score ≥ threshold（默认 0.6）；随后可自评覆盖（仅当 is_correct 为 NULL）。
ordering
新增		 {"order":[item_id,…]}（正确顺序的条目 id 序列）；可选 {"grading":{"mode":"position_ratio"}} {"order":[item_id,…]}（用户排列） exact（默认）：序列全等 → 1/0；position_ratio：score = 对位条目数/n，is_correct = 全对。校验：作答必须是该题条目 id 的完整排列。
matching
新增		 {"matches":[{"left":id,"right":id},…]}（覆盖全部左项、恰各一次）；可选 {"grading":{"mode":"pair_ratio"}} {"matches":[{"left":id,"right":id},…]} exact（默认）：全部配对正确 → 1/0；pair_ratio：score = 正确对数/左项数，is_correct = 全对。校验：left 覆盖全且不重复、right 存在且属于本题、one_to_one 时 right 不重复。
得分语义统一：score ∈ [0, max_score]（max_score 默认 1，沿用既有 CHECK），ratio 模式写入小数比率；is_correct 保持"布尔正确"语义——exact 全对为 true，ratio 模式默认仅全对记 true（保证 accuracy / weakQuestions 统计口径不被部分得分污染）。将来若要"达到阈值即算对"，在键中加 "passThreshold":0.6 即可，grade() 按钮一个分支消化，无需再动表。

2.5 兼容性论证（逐条）

  1. 1question_types 既有 4 行原样保留，既有题目三元外键不受 CHECK 扩列影响（新枚举只放宽、不收紧）。
  2. 2两张新子表均为独立新表，questions/practice_answers 只加可空列，任何既有行读写在迁移前后等价。
  3. 3grade() 对旧键形状完全兼容：fill_blank 旧扁平字符串按"单可接受答案"处理（str 与 [str] 两种元素等价）；简答键无 grading 块即维持 NULL 行为。
  4. 4既有端点的路径、方法、必填字段全部不变，新增字段均为可选（items / matchingVariant / groupId / review 端点），旧调用方零感知。
  5. 5考试模式答案屏蔽（exam 未交卷不下发 answer_key_payload / is_correct 等）逻辑与新题型正交，实现时把 items 相关键一并纳入屏蔽字段即可（见 §5-9）。

2.6 扩展性预留

  • 再增新题型的固定套路：扩 CHECK 枚举 → 注册 question_types 行 → 按需建 question_<mode>_items 风格子表 → normalize_key / validate_key / grade 三个函数各加一个分支 → 前端渲染器加一个分支。四处皆为本方案已验证的模式复制。
  • 判分策略演进不锁死：策略全部走键内 grading 块（JSON），新增策略只改 grade() 分支；键按版本不可变，策略随键版本演进，历史作答可复现当时的判分依据。
  • 按 subject 定制题型：question_types 的 UNIQUE(subject_id, id, answer_mode) 允许某学科注册专属题型行（如 'ordering' 的数学变体），前端题型选择器由 GET /question-types 驱动，零代码即可出现新项。
  • 完形/阅读理解类复合题：可复用 content_blocks（组级材料）+ 子题组，不需要新表；若未来需要"子题间共享作答状态"，再评估组级会话结构，当前刻意不做（见 §5-8）。

3. 前后端接口设计

3.1 通用约定（沿用现行机制，新端点自动继承）

  • 包络：成功 {"data": …, "meta": {"pagination": {"cursor","limit","hasMore"}}}；204 返回 {"data":null}。
  • 幂等：所有写请求（POST/PATCH/PUT/DELETE）必须携带 Idempotency-Key 头，缺失 422；同键同体重放返回缓存响应（request_idempotency 表）。
  • 命名：请求体 camelCase（Pydantic 严格模式 extra="forbid"），响应为数据库行 snake_case，题目页局部 camelCase（questionIndex/nextIndex 等）——与现状一致。
  • 错误：422 VALIDATION（形状/枚举/排列非法）、409 INVALID_STATE（状态机冲突，如发布无键、重复自评）、404 标准不存在。

3.3 场景详解

① 创建题目（排序题 / 连线题示例）

排序题——items 数组顺序即正确顺序，省略 answerPayload 时服务端按数组顺序生成键（插入拿到条目 id 后归一化为 {"order":[id,…]}）；也可传 0 基下标的显式顺序：

POST /api/v1/banks/3/questions        Idempotency-Key: create-q-001
{
  "questionTypeId": "ordering",
  "answerMode": "ordering",
  "stem": "将下列阶段按软件生命周期先后排序",
  "items": [
    {"content": "需求分析"}, {"content": "系统设计"},
    {"content": "编码实现"}, {"content": "测试验收"}
  ],
  "answerPayload": {},                 // 省略=按 items 顺序；或 {"order":[2,0,1,3]} 用下标表达
  "status": "active"
}

201 → {"data": { "id": 45, "answer_mode": "ordering",
        "items": [{"id":101,"content":"需求分析","sort_order":1}, …],
        "answer_keys": [{"version":1,"is_primary":true,"answer_payload":{"order":[101,102,103,104]}}], … }}

连线题——items 用 side 区分左右；answerPayload.matches 用 0 基数组下标表达配对，服务端归一化为条目 id：

POST /api/v1/banks/3/questions        Idempotency-Key: create-q-002
{
  "questionTypeId": "matching",
  "answerMode": "matching",
  "matchingVariant": "one_to_one",
  "stem": "将国家与对应首都连线",
  "items": [
    {"side":"left","content":"中国"}, {"side":"left","content":"法国"},
    {"side":"right","content":"巴黎"}, {"side":"right","content":"北京"}
  ],
  "answerPayload": {"matches":[{"left":0,"right":1},{"left":1,"right":0}]}
}

201 → { "data": { "id": 46, "matching_variant": "one_to_one",
         "items": [{"id":110,"side":"left","content":"中国"}, …],
         "answer_keys": [{"answer_payload":{"matches":[{"left":110,"right":113},{"left":111,"right":112}]}}] } }

创建期校验（QuestionIn.model_validator 扩展）：ordering ≥2 个条目；matching 左右各 ≥2 条，one_to_one 要求左右数量相等、每个左项恰配一次且右项不重复，many_to_one 允许右项复用；choice 既有校验（仅 choice 有 options）保持并扩展为"仅 ordering/matching 有 items"。

② 编辑题目

PATCH /banks/{bank_id}/questions/{qid} 传入 items 时全量替换（同侧删除后按传入顺序重建 sort_order），并在同一请求内携带 answerPayload（0 基下标，相对新 items 数组）——服务端替换条目后立即据此创建新版本答案键（原子完成，避免出现键悬空的中间态；新键继承旧键的解析说明）。若主键已存在而请求未带 answerPayload → 409 INVALID_STATE。仅改答案不改条目时仍走 answer-keys 端点（此时按条目 id 引用）。答案键受 immutable_answer 触发器保护不可变，历史作答仍指向旧键版本，可复现当时的判分依据。

→ { "data": { …, "answer_mode":"matching", "matching_variant":"one_to_one",

5. 关键权衡与注意事项

  1. 1独立子表 vs 通用 parts 表。选独立子表：强外键、唯一约束、排序约束在库层挡脏数据，查询直白，与项目"严格 Pydantic + 显式 SQL + 显式约束"哲学一致。通用 question_parts(kind, payload jsonb) 可零 DDL 加题型，但类型安全全部让位给应用层，长期看约束形同虚设。折中即本方案：结构进子表，判分配置进 jsonb。
  2. 2判分放应用层而非 PG 函数。沿用 grade()：单测好写、与现行实现一致、错误信息可读。代价是判分变更需发版；个人库无并发与性能压力，可接受。不建议把判分塞进 SQL/触发器（难测试、难表达集合/排列逻辑）。
  3. 3部分得分与统计口径。坚持 is_correct = 布尔"全对"，部分得分只进 score：accuracy、weakQuestions、按对错复习（mode='wrong'）的语义都不被稀释。若把 ratio≥0.6 记为"正确"，错题复习会漏掉半对题。可选 passThreshold 留在键里按需启用。
  4. 4答案键引用条目 id 的编辑联动。键不可变 + 条目可编辑，两者相遇必然出现"键悬空"。方案是编辑条目前置校验并要求先出新键版本（与选项删除的现行行为同构）。备选"用稳定 token 代替 id"被否：两套标识徒增对账复杂度，id + 版本化键已足够。
  5. 5归一化判分的误判风险。casefold + 空白折叠对英文友好，对中文同义表述、错别字无能为力——所以填空给"每空多可接受答案"由人工维护，简答关键词判分阈值默认 0.6 且永远保留自评兜底。自动判分是加速器不是裁判，这一立场写进产品文案与编辑器提示。
  6. 6CHECK 扩列的运维细节。DROP + ADD 瞬时持 ACCESS EXCLUSIVE 锁，个人库毫秒级完成；迁移一次性执行失败即回滚（BEGIN/COMMIT 包裹），不产生半迁移状态。新库走更新后的 00_schema.sql，两份 DDL 必须保持等价（建议 check_schema.py 加断言防漂移）。
  7. 7matching 变体建模。镜像 choice_variant 用一列 + 形状 CHECK，而不是拆两张表或再造 answer_mode：保持"一行一形态"直觉，且 many_to_one（分类题）无需新题型即被覆盖。one_to_one 的"左右数量相等"无法用库级 CHECK 跨行表达，落在应用层校验——这是有意的取舍（库层只挡行内/行间局部事实）。
  8. 8组合题刻意不做组级答案与组级判分。"每题一答一键一判"是练习/统计全链路的不变量（practice_answers UNIQUE(session_id, question_id)、错题、掌握度都建立在单题粒度上）。组只做材料容器 + 呈现顺序 + 展示层聚合；引入组级分数会同时破坏幂等作答、考试屏蔽、错题推导三处逻辑。
  9. 9考试模式屏蔽必须覆盖新字段。hidden() 现屏蔽 6 个判分相关字段；实现时 answer_key_payload 天然包含条目 id 顺序/配对（等于答案本体），务必沿用既有屏蔽路径，不要在 items 渲染时绕过（前端仅渲染条目 content，绝不渲染键）。
  10. 10AI 导入与生成链路是后续项。本方案只覆盖产品 API/DB/前端；server/src/practiq_ai 的文档抽取器与题目生成工作流需要另行支持排序/连线的识别与产出（含 answerPayload 归一化对齐），建议作为独立迭代，先让手工录入链路跑通。
  11. 11幂等与媒体约束自动沿用。新端点走既有 request_idempotency（route+key+request_hash）；条目暂为纯文本，若需图片走附录 A 的 media_links 扩列，媒体 10MiB 上限、checksum 去重机制原样复用。
  12. 12避免过度设计。不为"未来可能的题型"预建列/表；answer_mode 枚举 + jsonb + 固定套路已经把边际成本压到"一次 DDL + 三个分支"，足够敏捷。
