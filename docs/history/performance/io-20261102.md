# Verified I/O work reduction — November 2, 2026

Baseline: `55d742a0f59e6fca6e4058d9030ad57aacfb3418`. The candidate keeps the
existing service/desktop architecture, public APIs, schemas, backup formats,
credentials, explicit model triggers and unknown-result handling. No dependency
or configuration option is added.

## Changes

1. Repair restore skips a second staged-resource read when current bytes already
   pass size/hash verification. Full staging validation and the durable recovery
   inventory still precede database replacement.
2. New successful parser-unit summaries contain only their public visual
   references alongside the durable unit receipt. Authorization uses the current
   summary; old checkpoints retain verified unit-file loading. Requested bytes
   are always verified, including after a prior successful read.
3. File publication retains file and direct-parent synchronization. A bounded
   per-process map remembers successful ancestor synchronization only while the
   complete directory chain retains the same filesystem identities.
4. Binary upload uses incremental hashing and at most 1 MiB of batching for small
   chunks. Large incoming chunks are written directly. It preserves size/hash,
   Office-family validation, atomic publication, read-back verification, storage
   capacity, deadlines and cancellation-safe cleanup.
5. Flag, manual-score and review-completion responses reuse the current SQLite
   connection. No connection survives an operation or changes restore lifetime.
6. Short PostgreSQL operations reuse at most four connections. Rollback,
   cancellation, connection failure, independent readers and shutdown are tested;
   failed writes are never replayed.

## Service measurements

Run `server/scripts/benchmark_io.py --baseline 55d742a0 --output /tmp/io.json`
with the selected Python 3.14+ interpreter and `PYTHONPATH=src:.` from `server/`.
The script executes local Git baseline classes/functions and current code on
temporary files and disposable Docker PostgreSQL/RabbitMQ. Assertions verify
saved bytes, allowed references and all SQL write results. No provider is called.

The [final raw report](../../evidence/2026-11-02-io/service-final.json) includes
platform, Python version, probe/source hashes and all three alternating paired
samples. Tests and builds were stopped during these measurements. OS caches were
not flushed; first invocations remain included. Figures below are medians.

| Operation | Baseline | Candidate | Work evidence |
| --- | ---: | ---: | --- |
| Publish 100 small artifacts | 38.80 ms | 34.73 ms | File syncs remain 100; directory syncs 600 → 105 |
| Authorize 100 distinct figure references in 100 partial-result units | 2,165.46 ms | 2.27 ms | Unit-file loads 5,050 → 0 |
| Upload 17 MiB in 68 KiB chunks | 20.19 ms | 17.39 ms | Separate traced Python allocation peak 55,375,387 → 17,971,090 bytes |
| 30 durable PostgreSQL autocommit writes | 1,233.71 ms | 8.19 ms | Backend connections 30 → 1 |

Authorization timings cover membership checking, not checkpoint SQL, image
transfer or rendering; distinct references reuse the same synthetic PNG bytes.
Artifact timings include real syncs plus counting
instrumentation. Upload timings call the route with a generated request stream,
not TCP or browser upload; allocation peaks are separate instrumented runs,
not process RSS. PostgreSQL measures a local disposable deployment; connection
startup latency and production gains will differ. These are small synthetic
samples, not end-to-end import or user-latency promises.

The [initial report](../../evidence/2026-11-02-io/service-initial.json) retains
the rejected per-chunk upload approach: its median rose from 26.08 to 36.36 ms
despite lower memory. The [first batched report](../../evidence/2026-11-02-io/service-batched.json)
retains the next run, with nearly equal upload time. The final candidate adds
shared storage slots and explicit write deadlines; all source hashes are retained
separately. The [pre-cancellation-fix report](../../evidence/2026-11-02-io/service-pre-cancellation-fix.json)
retains the previous candidate's measurements. Full verification exposed a driver
transaction-entry cancellation case: PostgreSQL could report idle while psycopg
still held active transaction bookkeeping. That candidate is not accepted.
The final pool discards every failed/cancelled borrower, with a deterministic
regression for cancellation after driver transaction entry and the existing
ambiguous-broker-window tests. No run was removed to select a faster sample.

## Desktop measurements

`repair_asset_io_stress` runs the real release `Store::restore_recovering` with
one damaged resource. It creates deterministic one-pixel PNG resources in
temporary databases, runs one warmup and three measured calls, then reopens and
backs up every restored store. Timing includes validation, durable recovery copy,
repair and database publication; fixture setup and output checks are excluded.
Baseline and candidate executables were retained separately, and the clean
baseline run preceded the candidate with no concurrent build/test process.

| Resources | Baseline verified reads | Candidate verified reads | Baseline median | Candidate median |
| --- | ---: | ---: | ---: | ---: |
| 20 | 60 | 41 | 123.99 ms | 142.43 ms |
| 200 | 600 | 401 | 940.19 ms | 934.34 ms |

The [baseline](../../evidence/2026-11-02-io/repair-before.json) and
[candidate](../../evidence/2026-11-02-io/repair-after.json) preserve every sample.
The [initial diagnostic](../../evidence/2026-11-02-io/repair-initial-diagnostic.json)
overlapped a debug compilation and is retained but excluded from the clean comparison.
The optimization demonstrably removes N−D verified reads; these tiny-image
samples show no stable wall-clock benefit. The regression checks zero, one and
all damaged resources, and validates re-open and backup after repair.

The normal session-update regression counts actual SQLite opens: flag 3 → 1,
manual score 2 → 1, review completion 2 → 1. It checks saved flag, score and
completion state. There is no native interaction latency claim.

To reproduce native probes, compile both variants with the same test-only probe
and retain their executables before switching production sources:

```sh
TAURI_CONFIG='{"bundle":{"resources":[]}}' \
  cargo test --release --locked --manifest-path app/src-tauri/Cargo.toml \
  --lib repair_asset_io_stress --no-run
PRACTIQ_BENCH_OUTPUT=/tmp/repair.json "$TEST_BINARY" \
  backup::schema_tests::repair_asset_io_stress --exact --ignored
```

## Correctness and remaining limits

Both full checks passed on macOS 27.0.1 arm64 with Python 3.14.7:

- `make verify AI_PYTHON=/path/to/python3.14`: lock consistency, Ruff, Pyright,
  30 evaluation fixtures, 3,633 passing service tests, 93% coverage (90%
  required), recovery probes, source/wheel build and archive integrity checks.
- `make app-check AI_PYTHON=/path/to/python3.14`: generated-contract parity,
  51 shared contract fixtures plus the sample, frontend types/lint, 531 frontend
  tests (six skipped), 260 native tests (26 ignored), formatting and Clippy.
  Native coverage includes explicit damaged-resource recovery, publication
  failures, forced process termination around restore and sidecar recovery.
- Independent release repair probes and the service paired probe completed
  separately from tests/builds. Documentation links, evidence JSON, final
  source/probe hashes and `git diff --check` passed.

The first full service attempt exited in the broker cancellation test, leaving
incomplete coverage; it was not accepted. The deterministic transaction-entry
regression drove the pool fix described above. The next full run passed 3,632
tests and failed only the upload hash test's one-shot-only replacement for
`hashlib.sha256`. Its replacement now supports incremental `update()` and still
requires both incoming hashing and read-back hashing to run off the event loop,
while `/ok` responds during a gated hash. All 20 focused upload/projection tests
then passed, followed by the accepted complete `make verify` run. The coverage
threshold and recovery gates were never lowered.

Focused regressions cover expired/deleted/foreign task references, changed image
bytes, legacy checkpoints, Office uploads, byte limits, incomplete and cancelled
uploads, synchronization failure and directory replacement, bounded directory
tracking, transaction rollback, cancelled borrowers, broken connections and
shutdown. Existing restore fault/kill tests remain required.

No live providers, real user databases, GUI/installer run, physical power loss,
Linux runtime or whole-process RSS measurement was performed. Parser code changes
follow the existing execution-signature deployment rules: retain the original
deployment for unfinished imports instead of rewriting their signatures.
