Date: 2026-11-04. Result: **PASSED for local acceptance**.

The [machine-readable evidence](../../evidence/2026-11-04-rabbitmq/acceptance.json)

## Delivered behavior

- Publisher and consumer use separate TCP connections and independent reconnect
  loops. Publish failures preserve the outbox and do not close consumer ACKs.
  Consumer recovery retains ownership until old handlers/executions finish.
- Both connection roles, oldest pending age and finite sanitized failure reasons
  are observable. Wrapped TLS errors remain distinguishable without logging
  credentials or exception text. Broker endpoint credentials do not reach Office
  workers or the acceptance child environment.
- Direct node/queue Prometheus scraping and tested rules cover missing scrapes,
  resource pressure, missing consumers, dead letters, old pending work and repeated
  failures. The existing production preflight now requires this evidence.
- Broker resource budgets and mounted capacity policies retain `reject-publish`
  and at-least-once dead lettering. Full DLQ source retention survives a restart.
  Policy import is explicit and preserves existing queue declarations/volumes.
- An optional three-node profile and same-cluster endpoint failover preserve the
  single application owner. Both queues were verified with three members and the
  mounted policy import was checked against the actual management API.
- Read-only startup stays passive, consumes control wakeups without a busy loop,
  and supports the existing explicit resume after writable configuration returns.

## Activation and remaining boundaries

Follow the [resource/policy and cluster instructions](../../../server/docs/rabbitmq.md#resource-limits-policies-and-monitoring)
to apply configuration to a deployment. Existing brokers need explicit reviewed
policy import; the local tests did not alter an existing service or its volumes.
Inspect effective policies and member counts, provision restricted credentials,
and verify the actual alert receiver before production admission.

Hosted CI, live deployment, real alert delivery, production capacity, real model
quality/billing and cross-host/disk disaster recovery were not checked. All
brokers in the leader-kill drill ran on one Docker host. Full-service HA still
requires independent failure domains plus PostgreSQL/file-storage recovery.

## CI startup follow-up: 2026-11-05

The first hosted run failed before service tests: immediately after a broker
restart, `rabbitmqctl await_startup` could exit 69 before the Erlang node was
reachable. CI now retries the authenticated Management API and Prometheus HTTP
endpoint with a 60-second retry budget per endpoint and a 3-second request limit.
Configuration-copy failures and exhausted readiness retries still fail the job.
Web reports are uploaded only when the Web check actually ran; missing reports
from an executed check remain an error.

The workflow regression suite passed all 70 cases, including the unavailable
Erlang-node scenario and setup/HTTP failure propagation. Ruff and Pyright passed.
The actual workflow restart/readiness script passed against the pinned disposable
RabbitMQ image in 3.45 seconds, recovering from two initial empty HTTP replies.
This smoke used fixed host-port mappings, as hosted CI does; an earlier local
attempt with dynamically assigned host ports failed because restart changed them.
The full-suite evidence above remains the pre-follow-up snapshot at `c6e42e47`;
it does not claim to hash-bind this workflow correction or its added tests.
